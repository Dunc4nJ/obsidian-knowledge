- [[Lakebase puts Postgres on open object storage as a third database generation - O(1) branching, sub-500ms compute start, and 7x space amplification as the price]] — the VLDB 2026 paper from the Neon team at Databricks (Linnakangas, Shamgunov, Pandis, Ghodsi, Xin, Zaharia). **Gen-1** (Postgres/MySQL/Oracle) couples compute and storage on one machine; **Gen-2** (Aurora, Socrates, AlloyDB) separates them but "the separation remained internal to the vendor's architecture... data continued to be accessible only through the primary database engine"; **Gen-3** persists everything including WAL in *open* Postgres page format on object storage, so other engines read the same bytes — the one property that can't be retrofitted. Agentic workloads are the stated pressure, with production telemetry that's the best evidence in the paper: **many instances alive under 10 seconds**, **branch depth past 64**, a new compute started *per user prompt*. Storage splits into **Safekeepers** (Raft-like WAL quorum) and **Pageservers** (LSM delta/image layers, `GetPage@LSN`). **Branching is an O(1) metadata write** — but deep hierarchies hurt reads, since a miss recursively searches parent timelines, and the fix is operational (detach and promote to root). **P95 startup <500ms** from a warm pool plus offloaded crash recovery; without the pool, minutes with tails in hours. HammerDB TPROC-C: 2.6x over Gen-2 at 1 vCPU, **515.6K NOPM at 24 vCPU (+26% over Gen-2, 5.3x over Gen-1)** — though at 4 vCPU it sits *behind* Gen-1, a U-shaped result. Lakehouse integration is where open format cashes out: Unity Catalog identity with no ACL drift, **Direct-to-Storage ingestion up to 73.3x over COPY**, `wal2delta`, and Direct Access cutting TPC-H **10x**. Costs published honestly: **~7x space amplification** across the fleet, Q8/Q19 *slower* under Direct Access, 1.76x scan degradation under concurrent OLTP. Vendor paper against anonymized archetypes. 11 figures.

- [[Cursor's Continuity replaces GitHub Spokes three-phase commit with an S3 write-ahead log as the source of truth for Git hosting]] — Vicent Marti's engineering post behind **Origin**, Cursor's Git hosting product. Frames the problem as three places you can distribute Git — the filesystem, the packfiles, or Git itself — and walks the two dead ends: object-level storage in a DHT (Shawn Pearce's JGit work at Google) dies because "at every step of this walk, you don't know the value of the next pointer until you fetch the previous one" *and* the protocol still demands packfiles on the wire; GitHub's NFS/GFS/DRBD era dies because packfile layout is optimized for size, not traversal — objects placed randomly, delta-compressed, so logical hops become physical hops. **Spokes** (GitHub, 2013) got three things right that have held 13 years: don't distribute Git, keep real repositories on local NVMe, keep every copy consistent — with the elegant trick that only the *reference transaction* needs 3PC while packfiles fan out unsynchronized. Its two failures are the same failure in opposite directions: 3PC latency is bound by the slowest node so more replicas make pushes *worse*, and the floor of three replicas is absurd for the millions of throwaway repositories agents create. **Continuity** substitutes one thing — a write-ahead log in S3 is the source of truth — and nearly everything else falls away: no routing table, no relational database, no elections (atomic CAS on S3 serializes the log, so any node can be primary), rendezvous hashing only as an optimization, local repos as a garbage-collectable warm cache, UDP gossip for optimistic replication with correctness recovered by ETag-conditional GETs (`304` in <10ms), and compaction done once on the primary while replicas download compacted packs — bandwidth for CPU. Reported: 100 replicas with linear read scaling (**synthetic**), 120 pushes/s on S3 Standard, >300 pushes/s on S3 Express One Zone bottlenecked by Git's own compaction. Caveats worth carrying: vendor launch post, no availability/cost comparison, no answer for an S3 degradation (every read validates against it), and the one measured chart (`everysphere`) plots ~4k and ~16k pushes/*minute* — below both prose figures. 10 figures.
- [[Chroma's wal3 ports the 1996 Michael-Scott lock-free queue onto S3 conditional writes and builds the log twice - once for data, once for a setsum that proves it correct]] — Chroma's engineering post (Escriva, Pan, Krusinski, Kedia, Bashir) on the WAL behind their vector database, and the fourth WAL-on-object-storage design in this vault after **Continuity**, **Lakebase** and **Archil** — same S3 primitive, same year, independently. S3's **conditional writes** (GA Nov 2024) supply CAS, which lets them port [Michael and Scott's 1996 lock-free queue](https://dl.acm.org/doi/pdf/10.1145/224964.224988) literally onto object storage: linked-list nodes become `fragment` files allocated with **if-none-match**, the list header becomes a **`manifest`** updated with **if-match on its entire content**. The mental model is Bezos's — S3 as "malloc for the Internet," keys as opaque variable-sized pointers — and the transferable claim is that decades of memory-concurrency literature becomes applicable infrastructure design the moment a blob store ships CAS. Kafka is rejected for disks and a topic-routing shim, WarpStream for not being open source, CDC for not existing on their primitives. The second half is verification: **setsum**, an *associative and commutative* checksum giving **100% coverage** of the log in **O(1)** per append and trim, because the log is monotonic — so *digest(GC'd prefix) + digest(live) = digest(all)*, an invariant any independent binary can check. Order-independence is the actual idea; it makes digests composable across parties who share nothing else. It caught a real bug: **idempotent garbage collection failed** — re-collecting A,B from A,B,C should be a no-op and wasn't. The philosophy is the sell: build systems **twice, once for functionality and once for verification**, because reactive observability "represents the bare minimum level of care we should expect from our software vendors." Durability framing worth keeping: 11 nines is table stakes, but **operator error is far more likely than S3 losing data**, hence auditing delete paths. Escriva wrote HyperDex, so the team is serious — but this is a vendor blog with **zero quantitative claims**: no latency, no throughput, no request amplification, no GC overhead, no cost comparison. The only number is four months from prototype to production. 1 figure.
