## Model & attention architecture

The layer *above* serving — how the model itself stores, updates, and retrieves state, which sets what the KV cache and every optimization below have to work with.

- [[From GPT-2 to Kimi K3 - a visual worklog on how attention architecture evolved to fix the KV cache with linear attention, DeltaNet, gating, and hybrid retrieval]] — @waterloo_intern's illustrated worklog (22 figures) tracing GPT-2 (124M, 2019) → Kimi K3 (2.8T, 2026): the KV cache as an O(N) memory-bandwidth bottleneck → **linear attention** (ELU+1 feature map folds K/V into a constant D×D state) → **DeltaNet / Fast Weight Programmers** (read-then-write the delta to fix recoverability) → **chunked-parallel DeltaNet** (Householder reparameterization for hardware-efficient training) → **Gated DeltaNet** (Mamba-2 scalar decay + delta rule) → **Kimi Linear / KDA** (per-channel fine-grained gating, 6× decode throughput) → **Kimi K3** (23 macrocycles of 3 KDA + 1 MLA, latent-space MoE with 898 experts, SiTU, Gated MLA, blockwise AttnRes). Thesis: it's not scale — a fixed-capacity associative memory needs a learned eviction policy (gating/routing/decay) and attention is the best selective-read mechanism

## KV cache

- [[DeepSeek-V4.1-Flash cuts global KV cache to 890 bytes per token - a quarter of V4-Flash and 437x below V1 - by stacking cross-layer CSA2 reuse, FP4 caching, and a causal encoder-decoder]] — the **full DeepSeek-V4.1-Flash tech report** (51pp, 552B backbone multimodal MoE, 1M context, 45T pretraining tokens): KV cost decomposed into three multiplicative dimensions (entry size / sequence / layer) and attacked on all three at once by **CSA2**'s statically-assigned Full/Reindex/Reuse modes with cache-sharing and index-reuse *decoupled*, plus a **Hierarchical Sparse Indexer** (a Full-mode layer's blockwise scores build a ≤16,384-position candidate pool that makes deeper indexers constant-cost in context length) and **FP4 main-KV QAT** (E2M1 + E4M3 scale per 16 channels, NVFP4 minus the global scale) → **890 bytes/token global KV**, ~4x below V4-Flash and **437x below V1**, with Decode FLOPs near-flat (4K→1M context costs only +1/4); a **Causal Encoder-Decoder** projects decoder global KV from the final encoder hidden state for **8B activated params at prefill vs 16B at decode**, and **SWA Bounded Replay** (replay only the last `n_win`=128 tokens instead of `L × n_win`, accepting states that are *not* mathematically identical, then simulating the same replay during post-training) drops the persistent SSD/host cache to **~1/8** and evicts SWA KV to a minutes-TTL pool in 10% of host DRAM. Absorbs **DSpark** (3 blocks, SWA 128, 5 parallel draft positions, Markov + confidence heads; MTP dropped entirely; kept training alongside the backbone to accelerate RL/OPD rollouts) and **196B of Engram** conditional memory as shipped components. Post-training claims *zero* algorithmic novelty and spends itself on data and environment engineering: agent tasks formalized as **(problem, environment, verification system) triplets** scored on difficulty and correctness, with those scores used as reward to train the model to build better tasks; mocked-tool general-agent environments rebuilt from real returned workflow interfaces; coding environments constructed by a pipeline of feasibility/setup/solver/quality-inspection/repair agents with fail-to-pass and pass-to-pass points and an explicit hackability check; RL scaled across six scaffold families with checkpoint merging across runs; **DSec** running millions of concurrent sandboxes on a custom eventually-consistent placement engine (sub-NUMA partitioning lifts density ~1,000→2,500 containers/node) while containing agents that exploited real XFS/AppArmor CVEs, leaked answers from package mirrors, and deleted filesystems; and a **scalar reasoning-effort knob** (`b`∈1–100 in the system prompt, subgroup-relative advantage per `(x,b)`, exponentially decaying length penalty) exposed as the public API's max/high/low = 100/75/50, where 25→100 buys +9.2pt reasoning average for ~2.5x tokens but the 60–80 band already recovers most of it. Results: DeepSWE v1.1 **74.2** and Terminal-Bench 2.1 **90.6** edge past Opus-5, CyberGym 88.1 is open-source SOTA, but Terminal-Bench 4.0 **31.2 vs Opus-5's 51.8** marks the expert-domain long-horizon gap the authors themselves concede. Scaffold swing is 8.7pt on DeepSWE alone (mini-SWE 74.2 → OpenCode 65.5). All numbers self-reported; no independent replication. Direct sequel to [[camelAI self-hosts DeepSeek V4 Flash on 4x RTX PRO 6000 Blackwell for a fixed-cost free tier, with KV cache as the real bottleneck]]
- [[stochasm reads DeepSeek-V4.1-Flash's causal encoder-decoder as per-layer YOCO on the global CSA2 branch only - self-attention with prefilled KVs, not cross-attention]] — @stochasticchasm's 57-tweet live reaction thread (55 report screenshots, 10 Sep 2026) working through the V4.1-Flash report section by section: the load-bearing correction is that **CED is neither cross-attention nor multi-layer encoder access** — it is ordinary self-attention whose global KV arrives pre-filled as a per-layer linear projection of the *final* encoder hidden states, so the decoder reads encoder state *in the context of its own sequence so far*; the YOCO delta stated precisely (YOCO projects once and shares one identical cache across every upper layer, CED projects **uniquely per decoder layer and only for the global branch** of CSA2 while each layer's SWA branch stays local, and skips the projection at prefill entirely). Corrects the discourse — DeepSeek **does** cite YoCo in §2.2. Reads the design as convergence with HySparse, NSA, MoDA and V4's own CSA/HCA, calls pure CSA2 an improvement on V4's two unexplained compression frequencies, and lands the thesis line: "inference efficiency is now the sole purpose of architectural modifications." Open questions he raises and does not answer are kept separate from the paper's claims: why the first 2 of 20 layers are SWA-only, whether modality-specific experts should be encouraged or suppressed, why convs were dropped for Muon when Muon handles them via flattening, where `L_norm` comes from. The **architecture** node of the V4.1 cluster — pairs with the full report in [[DeepSeek-V4.1-Flash cuts global KV cache to 890 bytes per token - a quarter of V4-Flash and 437x below V1 - by stacking cross-layer CSA2 reuse, FP4 caching, and a causal encoder-decoder]] and the data-side read in [[Viv reads four data-generation trends out of DeepSeek V4.1 and Kimi K3 - solve-inspect-repair and per-domain pipelines are in DeepSeek's report, the knowledge graph is Kimi's alone]]
- [[paged attention applies OS virtual memory paging to KV cache and unlocks 2-4x LLM serving throughput]] — PagedAttention: OS-style virtual-memory paging of the KV cache; the canonical serving-throughput result
- [[Ramp Labs Latent Briefing compacts KV caches for efficient cross-agent memory sharing]] — KV-cache compaction technique (Attention Matching, NNLS/ridge solves, batched CUDA kernels, prefix caching, GPU↔CPU offload)

## GPU kernels & the hardware layer

The layer beneath serving: how the kernels every note above treats as a black box are actually built.

- [[Ahmad Osman's kernel curriculum - you don't run a model you run kernels, and here are eight mini-projects from RMSNorm in Triton to a custom op profiled inside vLLM]] — @TheAhmadOsman's thesis post plus the curriculum that follows it. **"You don't run a model — you run Kernels"**: the model is a graph, the engine is scheduler/optimizer/executor, and the work happens in MatMul / attention / RMSNorm / KV-cache / quantized-linear / sampling / fused kernels — same model, same GPU, same VRAM, wildly different performance, because the other stack is "playing hot potato with tensors through 47 tiny launches." Names the four engines by distinguishing mechanism (vLLM, SGLang, TensorRT-LLM, and **FlashInfer as the shared kernel library beneath them**, which is the tell), the theory list (Triton, CUTLASS/CuTe, FlashAttention, PagedAttention, MoE grouped GEMM, Nsight — "stop guessing"), and an **eight-step mini-project sequence** ending at integrating one custom op into vLLM or SGLang and profiling end-to-end. Reply adds a step 9 for checkpoints larger than every memory tier, where the target becomes **useful work per weight traversal** rather than tok/s; another notes prefix caching and RadixAttention are the same optimization. A compression, not a syllabus — the entry point to this section.
- [[Perplexity serves embeddings by treating them as a CPU-overhead problem - whole-model CUDA graphs and LazyTensors cut p50 from 4.60ms to 1.53ms while throughput stays at parity with vLLM]] — Perplexity Engineering on the stack behind `pplx-embed`: **Ivy** (Rust HTTP gateway — tokenization, templating, batch splitting, replica load-balancing) → **Tulip** (Rust/tokio/tonic gRPC scheduler) → **ROSE** (the Python LLM engine, reused wholesale). Central finding: for small embedding models the **CPU, not the GPU, is the bottleneck** — they track a per-model inflection point where GPU execution finally outcosts kernel launch, and it lands at thousands of tokens. Fixes are **whole-model CUDA graphs captured lazily** (a graph per sequence/token bucket, thousands of them, warmup on first hit and capture on second, spreading minutes of eager work over hours) and a **LazyTensor** (page-locked buffer + `cudaMemcpyAsync` + one event signalling both forward-pass completion and CPU availability) so Rust enqueues batch N+1 while N is still on device. Batch embedding is treated as compute-bound prefill, online embedding as memory-bound decode, so both reuse LLM kernels — no KV cache, ragged attention. **Read the charts, not the framing**: vs vLLM v0.22.0 on 1x H200 BF16, BGE-M3 at 128 tokens goes 4.60→1.53ms p50 and 7.96→1.67ms p99 (~3x / ~4.8x), but the gap compresses with sequence length and **indexing throughput is essentially at parity** — pplx-embed is 926.7 vs 902.3 emb/s at 512 and marginally *behind* at 1024 and 4096. Tail compression under concurrency is the sturdiest result. Also: FlashAttention 4 is not uniformly best — FlashInfer 3 wins on Qwen-based models at long sequences, so they keep multiple backends. Vendor post; much of the win is bought by specialization on known model shapes. 10 figures.
- [[agentic kernel development ships to production by profiling the whole model first - 42.3 percent latency cut on Qwen-Image]] — @BrianLi23: an agentic framework that closes the benchmark-to-production gap in kernel work. Four reasons winning KernelBench isn't shipping (workload-dependent configs, microbenchmark gains erased by CUDA graph capture/multi-stream, per-kernel work missing graph-level wins, serving-engine integration). Two layers: model-level optimization restructures the execution graph *first* (fusion, redundant-work elimination) so per-kernel optimization then improves the right kernels; a self-improving knowledge base retains passing kernels plus lessons from successes *and* failures, with production end-to-end latency as the reward signal. Results on SGLang/B300: **42.3% Qwen-Image**, 15.2% FLUX.2, 5.5% tok/s MiniMax M3 — headline wins are data-movement and redundancy (prepacked FP8 scales bit-identical at 7.3%/6.1%, fused QKV+epilogue 15.8%, bias absorption on ~11% of step time, a CFG modulation cache exploiting prompt-independence of timestep-only branches), plus per-kernel speedups to 4.6x. Honest asymmetry: mature LLM kernels yield only ~5.5% vs 42.3% on diffusion; 20 figures
- [[Chris Leary frames AI-written kernels as compilers 2.0 - the LLM is a stochastic optimizer in STOKE's seat, and semantic-equivalence checking is what makes not reading the kernel safe]] — the theory note under the two agentic-kernel entries above. Chris Leary (@cdleary — started **XLA**, 2+ years on OpenAI's hardware team) answers what the HotChips **Jalapeño MLA** talk left out: how can AI write a kernel nobody reads line by line? The frame is **superoptimization as search** — enumerating programs in objective order is intractable, **STOKE** (ASPLOS 2013) proposed an MCMC/Metropolis-Hastings random walk over program edits, and an LLM is the *smart-but-slow* substitute for that *dumb-but-fast* mutation: a **stochastic optimizer**, sitting where XLA's hand-written "lowering emitter" meta-program used to sit. Why it can beat the compiler is a claim about construction, not intelligence — classical optimizers are **local dataflow transforms run to fixed point** with **phase-ordered** pipelines (the composite scheduler–register-allocator being the famous casualty), which puts AI kernel work in the **program-synthesis** regime instead ("classic optimizing compilers won't see 'oh, you wrote a bubble sort'... and switch it to a quick-sort"). Price paid, stated plainly: unlike STOKE there is no as-time-goes-to-infinity optimality guarantee, only "human-like traction per unit time." **The load-bearing part is soundness and it is asserted, not shown** — "testing for semantic equivalence is possible and we do it," deferred to a future post; note *testing*, and note the slide's pipeline runs "functional kernel / executable tests" → "validated e2e on chip," i.e. differential testing whose coverage is the test suite's. The sharpest reply (@TonyJZhou) is the keeper: "a stochastic optimizer is only safe if the equivalence checker is sound, and then the checker becomes the compiler." One measured result, the HotChips slide: DeepSeek MLA **0.31% → 88.94% of roofline in ~41h** (FP8 attention matmuls 31.69% → attention rescaling with tiled lookahead 59.24% → value-matmul scheduling 77.14% → key-tile prefetch + coalesced scale access), GPT-OSS blocks **1.5-1.8x** over expert-written implementations — but 0.31% is a *functional-only* baseline, so only the 1.5-1.8x is like-for-like. Scope limit conceded in-thread to @filpizlo: this works because accelerator kernels are mathematical and dataflow-oriented and so admit "strong, complete contracts" — the licence to stop reading extends exactly as far as the contract, and no further. 3 figures

- [[NVIDIA's hardware-friendly LLM design guide - near-square tile-aligned dimensions, width over depth, NVFP4, and wide expert parallelism]] — the model-design bridge to this layer: NVIDIA's seven co-design guidelines for LLMs that saturate Blackwell GPUs — keep linear-layer dimensions near-square and multiples of 128/256/512 (arithmetic intensity + avoiding tile-quantization waste), prefer width over depth, design layers to be NVFP4-quantizable (15 vs 5 vs 2.5 PFLOPS FP4/FP8/FP16 on GB300, ~1pt of FP8 accuracy on DeepSeek-R1), and serve MoE with wide expert parallelism (DP attention + sharded experts), Chunked Pipeline Parallelism for disaggregated prefill, and Helix Parallelism (KV-cache sequence sharding) for the low-KV-head MQA/GQA/MLA latency regime
- [[MLC's Modern GPU Programming for MLSys is a Blackwell-era book that builds from the GPU execution model through TMA, tensor cores, and TMEM to a SOTA GEMM and Flash Attention 4 in the TIRx Python DSL]] — free MLC book/course; Blackwell execution & memory model, TMA, `tcgen05` tensor cores, TMEM, mbarriers, clusters, then a tiled→pipelined→warp-specialized GEMM and a full Flash Attention 4, all in the TIRx Python DSL
- [[Modal's GPU Glossary is a browsable reference that maps the GPU stack from device hardware through the CUDA software layers to performance concepts in ~80 linked terms]] — **reference/lookup resource** (not a synthesis): Modal's hyperlinked glossary of ~80 GPU terms across four layers — device hardware (SMs, tensor cores, TMA, memory), device software (CUDA thread/execution model), host software (driver/runtime/library stack + tooling), and performance (roofline, compute/memory-bound, arithmetic intensity, occupancy).
