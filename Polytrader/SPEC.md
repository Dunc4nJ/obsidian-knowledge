Technical Design for Polymarket and Kalshi Data Ingestion Infrastructure Overview and Objectives We aim to build a clean, robust data infrastructure to ingest and manage data from Polymarket and Kalshi prediction markets. This system should support both historical data analysis (for quantitative research and model training) and live data integration (for real-time models and analytics). Key objectives include: Comprehensiveness: Ingest all available data from Polymarket and Kalshi, including historical market data (prices, trades, metadata) and real-time updates going forward. Scalability: Design the pipeline to handle growth in data volume (Polymarket hosts thousands of markets ; Kalshi has ~1500 active markets ) and increased query loads, without significant reengineering. Cost Efficiency: Use storage and processing solutions that minimize cost (leveraging cloud object storage, on-demand/serverless processing, etc.) while still meeting performance needs. Data Quality and Cleanliness: Ensure the data is clean, well-structured, and easily accessible for researchers and models. Implement validation, deduplication, and proper schema design. Low Latency for Live Models: Provide a mechanism (such as a feature store or caching layer) for live models to retrieve the latest features/data with minimal latency (millisecond-level reads if possible). Flexibility: Remain cloud-agnostic where possible and use open-source or managed tools that integrate well. (We plan to deploy on the cloud, but we will research best practices across AWS, GCP, etc., and adopt what fits best.) Assumptions & Clarifications: (Since direct clarifications are not available, we state assumptions to proceed) Both Polymarket and Kalshi provide programmatic data access (confirmed via APIs and public data sources). We assume we have the necessary API access credentials (e.g. Kalshi API key, Polymarket builder API key) and any regulatory permissions required to fetch data. Data scope: We want all market data – including market metadata (contract details), time-series of prices/probabilities, trading volumes, and individual trades. Order book data might be available, but we will focus primarily on trades and price history unless order books are explicitly needed. Historical range: We need complete historical data (since each platform’s inception) and continuous updates for new data in real-time. Latency requirements: “Live integration” suggests near real-time updates for models. We assume that ingesting new data with sub-minute latency is sufficient (if truly sub-second is required for high-frequency trading, we can adapt with streaming tech, but we’ll target seconds-level latency for now). User familiarity: The team is familiar with Airflow and Python-based workflows. We assume they are comfortable with cloud services and possibly containerized or serverless deployments. They are • • 1 2 • • • • • • • • • 1 open to any cloud provider (AWS, GCP, etc.), so we will design a solution that can be implemented on common cloud stacks (with specific recommendations for each component). With these goals and assumptions, we will design a modular data pipeline comprising data ingestion, storage, processing/transformation (including a feature store for ML features), and orchestration/ monitoring. We will also discuss alternatives for each component and justify our recommendations to ensure the system meets the needs of a quantitative research environment and live predictive modeling. Data Sources and Requirements Polymarket Data: Polymarket is a decentralized prediction market platform (built on blockchain) with thousands of markets on various topics . Key data elements from Polymarket include: Market Metadata: Details of each market (question being asked, possible outcomes, market ID, creation/close time, etc.). This is typically accessible via Polymarket’s API (the Gamma API) or via their subgraph. We will need to fetch all markets and keep this updated as new markets are created. Trade Data: Every trade (or outcome token swap) on Polymarket’s order book. Polymarket provides a CLOB (Central Limit Order Book) REST API where “all historical trades can be fetched” . Each trade record includes timestamp, market ID, price, size, and possibly buyer/seller info. Because trades are recorded on-chain, there are some complexities (e.g. large trades might be split into multiple onchain events that need to be combined client-side , and trades have statuses like MATCHED, CONFIRMED, etc.). We need to capture all trades or at least all price-forming trades. Price Time-Series: We may derive this from trades (e.g. last trade price over time or VWAP per minute). Polymarket also offers a direct price history endpoint for convenience , which returns time-series data (timestamp and price) for a given market token. We might use this for quick historical retrieval or verification. Order Events: (Optional) If fine-grained data is needed, Polymarket’s on-chain order fill events can be retrieved via a GraphQL endpoint (e.g. Goldsky or TheGraph). This is what community tools do to reconstruct trades . For our purposes, fetching consolidated trade data via the REST API may suffice, but it’s good to note alternatives. Real-time updates: Polymarket has WebSocket feeds for live data (market channels for order book/ trades) and a Real-Time Data Stream (RTDS) . We can subscribe to these for push-based updates instead of polling. WebSocket authentication might be needed for private data, but market data may be public. This could yield low-latency updates for price changes and trades. Kalshi Data: Kalshi is a regulated event exchange with hundreds of markets (over 1500 active markets in 2025 ). Data elements include: Market Metadata: Information about each contract (ticker, description, expiration or event date, etc.). Kalshi likely provides endpoints or files for all markets. We know that “all-time market data [is] available on the website” , which suggests Kalshi publishes historical market listings or outcomes. Price/Trade Data: Kalshi’s API provides real-time market data (prices, order book snapshots, trades, volume, open interest, etc.) and the ability to execute trades . We will focus on retrieving market prices and trading activity. Potential sources: Public API: Kalshi’s REST API (with proper API keys and authentication) can return order books or recent trades for each market. The exact endpoints might include getting market price history, 1 • 3 • 4 5 • 6 7 • 8 9 • 10 2 • 11 • 12 • 2 current best bid/ask, last trade price, etc. . We will confirm and use the appropriate calls (the Zuplo guide suggests price history, order book depth, etc. are accessible ). Historical Data Files: Kalshi provides downloadable data (e.g., CSV files). The GitHub repository by mickbransfield indicates “Daily market data on the website” and “All-time market data available on the website” . These likely contain historical time-series or summaries for each market. We can use these as a one-time bulk import for history (which is more efficient than pulling years of data via API). Real-time Feed: Kalshi has a WebSocket API for real-time streaming of market data . By connecting to this, we can get live updates on trades or quotes for all markets (likely filtered by subscriptions). This will be crucial for low-latency updates to our system for live modeling. Outcome Data: As contracts resolve (e.g., an event outcome becomes known), Kalshi will have resolution data (which outcome paid $1). We should capture final outcomes for completeness. Polymarket likewise has resolution info (which could be inferred from final prices or an API endpoint for resolved markets). Unified Data Requirements: We will want to standardize data from both sources into a common schema where possible. For example, we might represent a “Market” entity with fields: source (Polymarket/Kalshi), market_id, question/description, outcome names, start/end times, etc. Likewise, a “Trade”/“PriceTick” entity with: source, market_id, timestamp, price (probability), volume, etc. Both sources produce time-series data (price over time, volume over time) which is critical for analysis. We will store fine-grained data (every trade or every minute price) to allow flexible research. We’ll also likely produce aggregated features (like daily volume, moving averages) for model consumption. High-Level Architecture Below is the high-level architecture of the data infrastructure, broken into functional components: Ingestion Layer (Data Sources to Raw Landing): Connect to Polymarket and Kalshi data sources (APIs, WebSockets, files) and ingest raw data. This will handle both one-off backfills (historical data) and continuous streaming of new data. The output of this layer is raw data stored in a durable staging area (e.g. cloud storage or a raw database table). Raw Data Storage (Data Lake): A scalable data lake to store all ingested raw data in tabular format. We plan to use a cloud object store (like AWS S3 or GCS) with partitioned files (e.g. Parquet/ CSV). This serves as the system of record for all historical data (and is cost-efficient for large volumes). Raw data can be reprocessed from here if needed. Processing & Transformation Layer: Processes that clean and transform the raw data into structured datasets and features. This includes: Parsing and structuring Polymarket’s raw trades/events (e.g., combine partial trades, convert units, attach market metadata). Merging data from multiple sources (if needed) into a unified schema. Calculating derived metrics/features (moving averages, volatility, etc.). 13 14 • 11 • 15 • 1. 2. 3. 4. 5. 6. 3 The output of this layer can be curated tables (e.g., a table of clean trades, a table of daily summary stats, etc.) stored in a warehouse or feature store. Feature Store / Serving Layer: A dedicated feature store or fast database for model features. The feature store holds the latest feature values in an online store (for live model inference) and the full historical feature values in an offline store (for training models) . Live models will query the online feature store to get real-time probabilities, trends, etc., with low latency. This layer ensures consistency between training and inference data and avoids re-computation during inference. Data Access & Consumption: Tools for researchers and models to access the data: Researchers (data scientists/quants) can query the data lake or data warehouse (using SQL or notebooks) to perform analysis, backtesting, and to develop new features or strategies. The ML models or trading algorithms can either query the feature store for needed features or subscribe to a stream of updates (depending on design). In many cases, the model service will request the latest features from the feature store at prediction time. We may also build internal dashboards or alerting systems that query this data (for example, a live dashboard of market probabilities, or triggers when certain conditions are met). Orchestration & Monitoring: An orchestration framework will coordinate scheduled tasks (batch jobs) and manage dependencies (e.g., ensure raw data ingestion completes before running a daily feature computation). We also include monitoring/alerting here: We’ll use something like Apache Airflow for scheduling ETL jobs (as the team is familiar). Airflow will run jobs for periodic ingestion, daily summarization, etc. (We will consider alternatives in a later section, but Airflow’s scheduling and dependency management is a strong choice for batch workflows). For the streaming components (which run continuously), we’ll rely on either a separate process manager (like a long-running service on Kubernetes or EC2) or integrate with a streaming platform (like Kafka) that inherently runs consumers continuously. Monitoring will be set up to ensure these streaming jobs are healthy. Logging and alerts: We will implement logging for all data flows and set up alerts (e.g., if no data received from Polymarket in X minutes, or if a job fails, etc.) so that issues are caught early. Data quality checks (possibly using Great Expectations or custom scripts) can run on new data to catch anomalies. Data Ingestion Layer Design The ingestion layer must pull data from Polymarket and Kalshi reliably, handling both initial backfill of historical data and continuous updates. We consider each source separately, then discuss integration: Polymarket Ingestion Historical Backfill (Polymarket): Polymarket does not officially provide a single bulk dump of all historical data, but we have a few strategies: Use the Polymarket REST API to fetch all trades for each market. For example, the “Get Trades” endpoint (via CLOB API) can be called repeatedly to page through all trades . We would need to iterate over all markets and collect their trades. This is a large task (Polymarket had 24,000+ markets created in one recent month alone ), but many markets are short-lived or low-volume. We’d implement a paged retrieval with rate-limit handling: Use the markets list from the API to get all market IDs. For each market, call the trades endpoint with pagination (if available, e.g., fetch 100 or 500 trades at a time) or with time ranges until all history is retrieved. The Polymarket API likely supports a start_time or offset parameter; if not, we can fetch “max” history in one call for each market, or use their price history API which might allow interval=max to get entire price series. This approach must obey Polymarket’s API rate limits – possibly by sleeping between requests or using an API key with higher limits. We’d include retry logic for transient failures and exponential backoff on rate-limit responses. Leverage community datasets as a shortcut. For instance, the Kaggle dataset of Polymarket data (if accessible) or open-source tools (like the poly_data GitHub project) can bootstrap our database. The poly_data project in particular outlines a pipeline: Fetch all markets via API (with batching and resume capability). Fetch all order-filled events via Goldsky (GraphQL) . Process events into trades . This suggests that using a GraphQL subgraph might be more efficient to get all historical trades (since TheGraph can return events by timestamp). However, relying on third-party indexing (Goldsky) might introduce another dependency. As an expert design, we could implement either route; a simpler initial path is to use Polymarket’s own REST endpoints, and only if performance is an issue consider TheGraph. • • • 4 18 • • • 7 19 • 20 • • 3 • 21 • 22 5 Real-Time Updates (Polymarket): For live integration, we want new trades (or price updates) as they happen: WebSocket Subscription: Polymarket’s documentation mentions a WebSocket for market channels . If feasible, we would connect to Polymarket’s WS and subscribe to either each active market or a global feed (if offered). Each trade or order book change would then be pushed to us in real-time. We would need to run a persistent service to maintain these socket connections and handle message processing. Scalability concern: If thousands of markets are active, subscribing to all might be heavy. We could optimize by only subscribing to markets of interest or throttle to key ones. But since we need “all data”, a better approach might be if Polymarket has a firehose stream of all trades. If not, we might opt for frequent polling for less active markets. Polling via API: Alternatively, we can poll the trades or price endpoint periodically (e.g. every minute or every few seconds). For example, we could call "get latest trades since timestamp T" repeatedly. If the API supports a startTs parameter , we can set startTs to last seen timestamp and fetch new data. This is simpler to implement (no persistent connection issues), but introduces slight latency and load. Given moderate trade frequency, a 30-second or 60-second poll could be acceptable if true real-time is not critical. Combination: We might use WebSockets for high-volume markets (like a major election contract during peak trading) to ensure minimal latency, and use periodic polling for the rest to reduce connection overhead. This is an optimization if needed. All ingested Polymarket data, whether from backfill or streaming, will be written to our raw storage with an identifier (market ID, timestamps, etc.). We should also store market metadata from Polymarket: - A job to fetch the list of all markets (with their details) should run regularly (say daily, or whenever new markets might appear). The Polymarket API provides market listings , and the poly_data tool fetches 500 at a time with offset . - Market metadata is relatively small; we can store it in a CSV/Parquet ( markets table) and also possibly load into a small database for quick lookup by other processes (like a Postgres or a keyvalue store mapping market_id to attributes). Checkpointing and Resilience: The Polymarket ingestion must keep track of where it left off to avoid duplicate data or data loss: - When backfilling trades by market, we mark a market as done (or store last fetched trade ID/time) so we can resume if the job is interrupted . - For streaming, if using WS, we might occasionally reconcile with the REST API (to catch any missed events if the socket disconnected). - Our pipeline should handle retries, failures, and data consistency. According to best practices, we’ll implement: - Idempotent reprocessing: If we re-run an ingestion for a given time window, it should produce the same data (so either avoid duplicates or have a way to overwrite/merge duplicates). - Deduplication: Polymarket data might have duplicates (the open-source tool explicitly handles deduplication of events ). We will ensure our storage or processing layer can deduplicate by transaction hash or unique ID. - Error handling: Automatic retries on network errors, and graceful handling of API errors (429 rate limits with backoff, 500 server errors with retry, etc.) . Kalshi Ingestion Historical Backfill (Kalshi): For Kalshi, we fortunately have easier access to historical data: - Official Data Exports: As mentioned, Kalshi provides “all-time market data” on their site . We will use scripts (like those in the GitHub repo) to download these files. They might be CSVs listing all historical price data or • 10 • • 23 • 24 3 25 26 27 11 6 perhaps snapshots of each market’s history. If they are daily snapshots, we can iterate over each day’s file (the GitHub shows files like kalshi_API_public_markets_2022-05-17.csv which suggests daily dumps). - We will download and consolidate these into our storage. For example, if each file is per day, we combine them to get the full timeline per market. This might be done via a batch job (using Python/Pandas or Spark) to read all CSVs and append them into a unified Kalshi trades/prices dataset. - If an “all-time” file exists, even better: we ingest that directly. - API backfill: In addition to or instead of files, we could use Kalshi’s API to pull historical data. The API might allow querying historical trades or candles. However, using the provided files is likely more efficient and won’t hit rate limits. We might still use the API to verify data or fetch anything missing. - Market listings and metadata: We should capture all existing market definitions from Kalshi. Possibly the data files include this, or the API can list all markets (active and expired). We’ll create a kalshi_markets table with fields like ticker, description, start/end, etc. Real-Time Updates (Kalshi): For live data: - WebSocket API: We will connect to Kalshi’s WebSocket feed for real-time market data. Kalshi likely allows subscribing to specific market tickers. We will subscribe either to all active markets or to a broad feed if available. Through the socket, we expect to receive events such as trade executions or best bid/ask updates. For our purposes, capturing the last traded price or mid-price at frequent intervals might be enough. If the feed is granular (order book changes), we might focus on trade events or use the mid-price to update our time-series. - Polling as fallback: If for any reason WebSocket is not viable (e.g., connection limits or complexity), we can poll the API for each market’s latest price periodically. But since Kalshi is regulated and user-focused, their API might not allow extremely frequent polling for all markets without an official data agreement. WebSocket is the intended mechanism for realtime, so we prefer that for timeliness and efficiency. - Writing streaming data: As with Polymarket, the incoming Kalshi updates will be written to raw storage. This might be append-only logs of trades or oneminute bars. One approach is to buffer real-time data in memory and flush to disk every N seconds or upon X events to avoid too many small writes. Alternatively, using a streaming sink (like a Kinesis Data Firehose or Kafka) can collect events and batch write to storage automatically every few seconds. Integration between Historical and Live: We need to ensure that after the initial backfill, the live data ingestion picks up where historical left off without gaps or overlaps. A typical strategy: - After loading all historical data up to date T (e.g., up to yesterday), configure the live ingestion to start from T onward. For example, if our historical files cover up to 23:59 of the previous day, the live feed from the API will handle today’s data. - There might be a slight overlap (e.g., if daily files include up to midnight and live starts just after midnight). We can handle overlaps by deduplicating on timestamp and price in the processing layer, or by designing a small buffer window. - Conversely, to protect against missed real-time data (if our service was down), we can periodically reconcile: e.g., each night fetch the official daily file for yesterday from Kalshi and use it to correct any missing records in our store. Security and Access: Both APIs require credentials: - Kalshi’s API keys (which we’ll store securely, e.g., in a cloud secrets manager, and use in our ingestion jobs). - Polymarket’s public data might not need auth for GET requests, but if API keys (builder keys) improve rate limits or allow WebSocket auth, we will use them similarly stored securely. - All connections will be HTTPS/WSS. We should also handle any required login or token refresh for Kalshi (their API might have an authentication token flow). Ingestion Implementation and Tooling Option 1: Custom Ingestion Scripts + Airflow: Given the specific nature of these sources, writing custom Python scripts to call the APIs and process the responses is a straightforward approach: - We can 28 15 7 implement these as Airflow DAG tasks for scheduled runs (e.g., a DAG for Polymarket backfill, one for daily Polymarket incremental sync, one for continuous Kalshi daily file fetch, etc.). Airflow can also trigger a realtime process, though Airflow is not event-driven; we might instead use Airflow to monitor that a streaming service is running. - The scripts will use libraries like requests for REST APIs and websockets or websocket-client for WS feeds. They will parse JSON responses and write to storage. - Using Airflow ensures we have easy logging, retry mechanism (Airflow tasks can retry on failure), and scheduling. For example, an Airflow task could run every minute to poll Polymarket if we choose polling. Option 2: Streaming Pipeline (Kafka/Kinesis): To decouple ingestion from storage, we could introduce a message queue or streaming platform: - For example, a small producer script (or Kafka Connect source) writes Polymarket trade events into a Kafka topic “polymarket_trades”. Similarly, Kalshi events into “kalshi_trades”. Then separate consumer processes read from those topics and handle writing to storage and updating features. - This can improve reliability (e.g., if the consumer is slow, the data is buffered in Kafka; if a service goes down, data still persists in the queue). It also scales: multiple consumers can handle partitions in parallel. - Recommendation: Given the scale here (likely a few thousand events per hour, not millions per second), a full Kafka cluster might be overkill. However, using a managed service like AWS Kinesis or Google Pub/Sub could provide the buffering with less ops overhead. For AWS, Kinesis Data Firehose is an attractive option: it can receive streaming events and directly batch-write to S3 with configured intervals. We could push incoming JSON events to a Firehose delivery stream which writes to s3://.../raw/polymarket_trades/YYYY-MM-DD/ files every minute for example. - If ultra-low latency processing of each event is required (for immediate feature calc), a Kafka/Kinesis consumer can be near real-time. But if writing to S3 with a 60-second batch delay is acceptable, Firehose simplifies things significantly (no servers to manage and fairly cost-efficient for moderate throughput). Option 3: Managed Ingestion Tools: Solutions like Airbyte or Fivetran have many connectors, but likely none built-in for Polymarket/Kalshi. They allow custom API connectors, but since we require fine control (especially for streaming via WebSockets, which those tools don't handle well), they are not a great fit outof-the-box. We can mention them for completeness as an option to ingest via REST on a schedule, but we’d likely have to code custom connectors anyway. Recommendation – Ingestion: We recommend a custom ingestion pipeline using Python and possibly lightweight streaming tools: - Use Airflow to orchestrate the historical backfill jobs and periodic sync jobs. - For the continuous streaming, run a dedicated process (or set of processes) for Polymarket and for Kalshi. For instance, a Polymarket listener service that handles WS messages and a Kalshi listener service similarly. These could be deployed as Docker containers on a cloud service (AWS ECS or Fargate, GCP Cloud Run, or simply a small EC2/VM). If using Kubernetes, one could deploy them as deployments for autorestart. - Have these listeners push data to our storage. To improve reliability, we might make them push to an intermediary (like Kinesis Firehose as mentioned, or even directly to the feature store for immediate use, while also logging to storage). - Ensure these processes have built-in reconnection logic (e.g., if WebSocket disconnects, reconnect and skip duplicates appropriately). - For simplicity and cost, we might avoid standing up a full Kafka cluster. Instead, an AWS-centric implementation might be: Polymarket WS → AWS Lambda (via API Gateway or some push?) or more directly, Polymarket WS → an EC2 instance that calls Firehose → S3. On GCP: use Pub/Sub to ingest messages and Dataflow to write to storage. - Since the team is open to cloud, using cloud-native serverless services for ingestion can reduce maintenance. For example, AWS Lambda cannot directly maintain a WebSocket to an external source indefinitely (since Lambdas are shortlived), so a small EC2 instance or Fargate container is more suitable for the WS client. That container can send each message to a Kinesis Firehose stream with a simple HTTP call (Firehose API) and Firehose will 8 handle batching to S3 . This design offloads the file writing logic and ensures exactly-once delivery to storage (Firehose will retry on fail and maintain order per key). - Meanwhile, Airflow scheduled jobs will handle tasks like daily downloading Kalshi’s new data file (if any), housekeeping (deleting any temp files, etc.), and running batch feature computations. The ingestion layer is thus a mix of streaming (for live) and batch (for historical/upkeep). By carefully combining these, we cover both needs. Next, we move to how we store all this data. Raw Data Storage Layer (Data Lake) To enable scalable analysis and reprocessing, we will store all raw data in a cloud-based data lake. This provides a single source of truth that can be used for various purposes (recompute features, try new transformations, feed into different tools). Storage Choice: We propose using cloud object storage (such as Amazon S3, Google Cloud Storage, or Azure Blob Storage) as the backbone of the data lake. This storage scales practically infinitely, is very costeffective (pay per GB stored), and can be accessed by many processing frameworks. It also decouples storage from compute – a big advantage for scalability and cost. Data Organization: We will organize the bucket with a clear directory structure and file format: - Use a partitioned folder structure by data source, data type, and date. For example: s3://prediction-data-lake/polymarket/trades/YYYY=2025/MM=11/DD=01/ polymarket_trades_2025-11-01_part00.parquet s3://prediction-data-lake/polymarket/markets/polymarket_markets_2025-11-01.json (market metadata snapshots) s3://prediction-data-lake/kalshi/prices/YYYY=2025/MM=11/DD=01/ kalshi_prices_2025-11-01.csv This partitioning by date (and possibly market ID for large tables) will allow efficient querying later (pruning data by date range, etc.), and it keeps file sizes manageable. - File format: We lean towards storing data in Parquet or ORC format for the fact tables (trades/prices). Parquet is a columnar, compressed format that significantly reduces storage size and speeds up analytics queries due to column pruning. It’s supported by most data processing tools. For smaller reference data (market metadata), JSON or CSV is fine, but we might still convert those to Parquet for consistency. - The data schema for each file type will be well-defined (e.g., trades table columns: timestamp, market_id, price, size, ...). We should use a data catalog (like AWS Glue Data Catalog or Hive Metastore, or even a tool like Databricks or Lake Formation) to register these tables. This way, tools like Athena (AWS) or BigQuery (GCP) can directly query the data lake using SQL. Handling Raw vs Processed Data: We might choose to keep raw data exactly as ingested (especially if it’s semi-structured JSON) in one area, and have a processed/cleaned version in another. For example: - Raw Polymarket trade events (perhaps storing exactly what the API returned, in JSON or as flattened CSV) in a “raw” prefix. - A cleaned version where we have standardized columns (which might involve some transformation). However, since we plan a separate transformation layer, we can consider the output of that layer as separate datasets. So: - Raw zone: strictly the data as initially recorded (for auditability). - Staging/ processed zone: data after initial cleaning (e.g., converting Polymarket’s raw order events into a proper 29 30 9 trade log as done by poly_data tool ). - Feature zone: curated feature tables ready for analysis or model use. Maintaining raw archives is cheap on S3 and provides the ability to re-parse if our understanding of the data improves or if we need to extract new fields. Data Volume Considerations: We should estimate and plan for data size: - Polymarket: If billions in volume, how many trades? Let's say Polymarket had $3.3B volume for an election . If average trade size is say $100, that’s on the order of 33 million trades in a short period (just an estimate; actual numbers would vary). Over years, possibly tens of millions of trade records. Parquet can handle that size (especially partitioned by date and market). It might be a few GBs of data. S3 can handle it, and tools like Spark/Presto can query it with partition pruning. - Kalshi: $7.5B in 15 months , likely also millions of trades. However, Kalshi’s daily data might be more summarized (or maybe tick-level, we need to confirm). We should plan for similar scale. Possibly smaller since Kalshi launched more recently. - A single trade record in Parquet is maybe a few hundred bytes, so 10 million trades ~ a few GB uncompressed, maybe <1 GB compressed Parquet. So raw storage needs are not huge (even 100 million records could be ~10 GB). - If we store order book updates or every quote, that could be bigger. We currently focus on trades/prices only. Data Warehouse (optional): In addition to the raw files, we might use a data warehouse for easier querying by analysts. This could be: - Amazon Athena or AWS Redshift Spectrum: which query the S3 data in place (Athena is serverless Presto/Trino). Athena allows SQL queries on our Parquet files without loading them into a separate DB, which is very convenient and cost-efficient (pay per query scanned). - Google BigQuery: We could directly load Parquet or CSV data into BigQuery tables. BigQuery can also query external data on Cloud Storage, or we could ingest it fully. BigQuery’s advantage is extremely fast SQL analytics and ease of use, but it has storage costs and query costs. For large historical analysis, it might be worth it. Since the user is open to cloud, BigQuery is a candidate if they prefer SQL-heavy analysis. - Snowflake or ClickHouse: If the team wants a dedicated analytical DB, these are options. Snowflake can query data in S3 (External tables) or ingest it; ClickHouse could be self-hosted for ultra-fast time-series queries (it’s very good at that). Feature Engineering and Feature Store Now we create a feature pipeline to generate the indicators and aggregated metrics needed by our models. There are two broad categories of features: 1. Time-series features per market – e.g., rolling metrics like moving averages of price, volatility (std dev of price changes) over certain windows, trading volume in last hour/day, momentum indicators, etc. These are derived from the sequence of trades or price points. 2. Cross-sectional or metadata features – e.g., how far from expiration the market is (time to event), liquidity measures (order book depth if available, or open interest in Kalshi), etc. Some may come from external sources (not mentioned here, but possibly e.g., related news sentiment – though that’s outside current scope). Batch Feature Computation (Offline): For historical analysis and model training, we will compute features over the entire dataset: - For example, compute a 5-day moving average of closing price for each market on each day, for all historical days. This yields a feature "MA5" that can be used in training models to predict something (maybe price changes or arbitrage opportunities). - Many such features can be computed in batch using the cleaned data tables. This is essentially a batch ETL on the data lake. Tools: - Spark is useful if 36 12 doing a lot of window functions or groupBy on big data. Python/Pandas could also do it but might be slower for very large data. - We might incorporate this into the DBT/SQL layer if the data is in a warehouse. For example, BigQuery can compute window functions per market fairly easily in SQL. This could simplify feature engineering with SQL. - There’s also specialized libraries (like tsfresh in Python or featuretools) for automated feature extraction from time-series. But given domain knowledge, we likely hand-pick features. - The result of batch feature computation is stored in the offline feature store. Concretely, this could be a Parquet table or a database table keyed by (market_id, timestamp) with columns for each feature. For instance, a table market_features_daily or even market_features_hourly . - We should store the event time with each feature and ensure a point-in-time correct dataset (so we can train models without label leakage). Each feature row should only use information up to that timestamp (which we’ll naturally do by how we compute it). Real-Time Feature Updates (Online): For live models, we need to update features as new data comes in. Two approaches: - On-demand calculation: When a model needs to make a prediction, it could fetch the recent raw data and compute features on the fly. This is not ideal for complex features or low latency needs, as it could be slow and inconsistent. - Pre-computation via streaming: Instead, we set up a process that continuously updates feature values upon new events: - For example, maintain a rolling window of last 100 trades for each market; when a new trade arrives, update the average price or volatility metric incrementally. - This could be done in the same ingestion consumer (embedding some feature calc in the data ingestion code) or as a separate streaming computation consumer. - Tools like Apache Flink or Kafka Streams are designed for stateful streaming computations (e.g., maintaining a moving average per key (market) and updating it with each new event). We could leverage such a framework for elegance and exactly-once processing guarantees. A simpler route is to code it ourselves using a dictionary of states in a Python process (since volume is not huge, one process can handle thousands of markets in memory). - Example: A Python streaming process subscribes to new trades (from the message queue or via callback in WS client) and for each trade for market X: - It updates a running sum and count for the last N trades, or keeps a deque of recent trades to compute windowed stats. - It then writes the updated feature values to the online feature store (or directly to the model if tightly integrated, but using a store decouples it). - Online Feature Store: We need a fast-access storage for latest features. Options include: - Redis (inmemory key-value store) – very low latency, but need to manage persistence (snapshotting) and clustering if scale out. Could easily store a hash per market with feature values. - AWS DynamoDB – used by SageMaker Feature Store for the online store . Dynamo can handle high write/read rates and is fully managed. Latency is ~millisec to low tens of ms for reads (with proper provisioning or On-Demand capacity). - Aurora or RDS (Postgres) – a relational DB can store latest features (market_id as primary key, and columns for each feature). Reads can be fast if indexed, but high update frequency might be an issue at scale. Also, adding features means altering schema (not a big deal with few features, but less flexible). - Feature Store Products: If on AWS, SageMaker Feature Store provides an API to put and get features, backed by Dynamo for online and S3 for offline . On GCP, Vertex AI Feature Store is similar (backed by their Spanner or BigTable I believe). Feast is an open-source feature store that can work with multiple backends (e.g., BigQuery offline, Redis online or Dynamo etc.). Feast could be an interesting choice if we want an open solution with a Python SDK to retrieve features. It requires some setup (deploying a Feast serving if not using their cloud). - Given the team’s familiarity and the complexity overhead, a simpler custom solution might suffice initially: e.g., use DynamoDB directly as a key-value store for features (with market_id as the key, a JSON or map attribute for features). Or use Redis if we prefer in-memory speed and can tolerate managing it (maybe use AWS Elasticache Redis to not manage VMs). - Recommendation: If using AWS, leverage SageMaker Feature Store for a fully managed solution to avoid reinventing wheels. It inherently provides an online store (Dynamo) and offline store (S3 Parquet) that sync, plus nice integration 16 37 16 13 with model inference. We can ingest streaming features via its PutRecord API . This ensures that whenever we update an online feature, it also appends to offline store (so history of feature values is saved) . This addresses consistency (training on the exact features that were available at prediction time). - If not AWS or to avoid service lock-in, Feast is a good alternative. We could have offline features in our data lake or BigQuery, and online in Redis. Feast provides a unified interface. - We will define Feature Groups such as “market_hourly_features” with fields like market_id, timestamp, price_change_1h, vol_24h, etc. The online store will only keep the latest timestamp per market (since it's key by market_id, which gets updated), whereas offline will accumulate historical records . - Feature Refresh Frequency: Some features might update on every trade (e.g., last trade price), others maybe every minute (e.g., recompute 5- min volatility). We need to balance freshness vs. compute: - For something like current price or last 5 trades avg, we update with every trade easily. - For a more expensive feature (say a prediction from a secondary model or an NLP analysis of news), we might do it less frequently. - We can design the streaming updater to handle multiple feature update schedules (e.g., a periodic trigger for certain aggregations and an event trigger for others). - Backfill in Feature Store: After computing historical features in batch, we should load them into the offline store (so that we can train models from the feature store directly). Many feature store systems allow directly ingesting historical data in bulk. For example, SageMaker Feature Store offline is just S3 files, so our batch job can write to those files (or we call their API in a loop for each record, but that’s slower – better to write to S3 and let the catalog pick it up). Feast allows ingesting a batch DataFrame of features to the offline store and even to online if desired. Ensuring Consistency and Accuracy: We must avoid training-serving skew (where features during model training differ from features at inference time) . By using the feature store for both, we minimize this risk: - The same code definitions for features are applied in batch and streaming. - We use the feature store’s point-in-time query capability (some feature stores or our own logic) to retrieve features aligned with historical ground truth events. Example Feature Workflow: 1. A new trade comes in for market X at time t with price P. 2. The streaming ingestion writes the raw trade to S3 (for history) and also notifies the feature updater. 3. The feature updater updates: - Last price = P - Price change 1h = P minus the price from 1 hour ago (which it has stored or can compute if it has a small buffer of past data; or this might be done by comparing to a feature stored for 1h window). - Rolling volatility 1h = update running variance with the new data. - Volume last 10 min = add this trade volume and drop any trades older than 10 min from the sum. (These are examples; actual features to be decided based on research needs). 4. It then calls PutRecord or writes to DB to update these features in the online store for market X . 5. Later, when the model wants to predict something for market X, it queries the feature store’s online API (or the DB directly) to get the latest feature values nearly instantaneously, and uses them. Meanwhile, offline: - Each day, a batch job might compute an end-of-day summary for market X (like total volume, high/low price, etc.) and store that in offline features for long-term analysis. - If needed, those daily features could also be put in the online store if models use them and they only change daily. By splitting responsibilities, we ensure fresh data for live models and rich historical data for training. 38 30 17 39 16 17 40 38 30 14 Tools and Frameworks for Feature Store: As mentioned, the main options are: - Cloud-managed Feature Store: SageMaker Feature Store (AWS) or Vertex Feature Store (GCP). - Open Source: Feast, or even simple custom solution (like a combination of Parquet + Redis). - Hybrid: Use a data warehouse as offline store and a custom KV store as online. If not using AWS, consider Feast (with, say, GCP BigQuery + Redis). But only if the team has the bandwidth to learn and manage it. If starting small, one could initially not set up a feature store and instead use a simpler approach (like a Python dictionary or Pandas DataFrame updated in memory for features) during prototyping.
